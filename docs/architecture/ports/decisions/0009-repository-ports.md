## Context

The collaboration and identity capabilities own the system's relational data: users, documents, workspaces, members, shares, attachments. Today these are SQLModel models manipulated directly from the FastAPI route layer. The use-cases need to *operate on* this data without importing SQLModel.

Three ways to expose persistence to the core:

1. **A single `Database` port** with hundreds of methods spanning all tables.
2. **Repository per aggregate** — one port per logical group of related entities.
3. **Generic `Repository[T]` parameterized by entity type** — one port shape, many instances.

Option 1 becomes a god-object. Option 3 is elegant but tends to require either dynamic dispatch or per-entity subclasses that look like Option 2 anyway. Option 2 is the conventional DDD pattern and matches the bounded contexts (collaboration, identity).

## Decision

One repository port per aggregate:

```python
class UserRepository(Protocol):
    async def create(self, user: User) -> User: ...
    async def get(self, user_id: UserId) -> User | None: ...
    async def get_by_email(self, email: str) -> User | None: ...
    async def get_by_username(self, username: str) -> User | None: ...
    async def update(self, user: User) -> User: ...
    async def delete(self, user_id: UserId) -> None: ...
    async def search(self, query: str, *, limit: int = 50) -> list[User]: ...

class WorkspaceRepository(Protocol):
    async def create(self, workspace: Workspace) -> Workspace: ...
    async def get(self, workspace_id: WorkspaceId) -> Workspace | None: ...
    async def list_for_user(self, user_id: UserId) -> list[Workspace]: ...
    async def update(self, workspace: Workspace) -> Workspace: ...
    async def delete(self, workspace_id: WorkspaceId) -> None: ...
    async def add_member(self, member: WorkspaceMember) -> None: ...
    async def remove_member(self, workspace_id: WorkspaceId, user_id: UserId) -> None: ...
    async def list_members(self, workspace_id: WorkspaceId) -> list[WorkspaceMember]: ...
    async def get_role(self, workspace_id: WorkspaceId, user_id: UserId) -> WorkspaceRole | None: ...

class DocumentRepository(Protocol):
    async def create(self, document: Document) -> Document: ...
    async def get(self, document_id: DocumentId) -> Document | None: ...
    async def list_for_user(self, user_id: UserId, *, workspace_id: WorkspaceId | None = None) -> list[Document]: ...
    async def update(self, document: Document) -> Document: ...
    async def delete(self, document_id: DocumentId) -> None: ...
    async def add_share(self, share: DocumentShare) -> None: ...
    async def remove_share(self, document_id: DocumentId, user_id: UserId) -> None: ...
    async def list_shares(self, document_id: DocumentId) -> list[DocumentShare]: ...
    async def get_effective_access(self, document_id: DocumentId, user_id: UserId) -> DocumentAccess: ...

class AttachmentRepository(Protocol):
    async def create(self, attachment: Attachment) -> Attachment: ...
    async def get(self, attachment_id: AttachmentId) -> Attachment | None: ...
    async def list_for_document(self, document_id: DocumentId) -> list[Attachment]: ...
    async def delete(self, attachment_id: AttachmentId) -> None: ...
```

The repository encapsulates the persistence model — the use-case does not know whether the underlying store is one table or four with joins. `WorkspaceMember` and `DocumentShare` are owned by their respective aggregate's repository because they have no meaning outside.

`DocumentRepository.get_effective_access` is a port method (not a use-case helper) because the access-resolution query is most efficient when the storage layer expresses it — e.g., a single SQL query joining three sources of grant.

## Consequences

**Easy:**
- Each repository is a small, cohesive interface. Implementing an adapter is mechanical.
- Use-cases declare what data they touch via their constructor signature. `ShareDocument` takes `DocumentRepository`; it cannot accidentally touch workspaces.
- Cross-aggregate consistency (e.g., "user has access to workspace X *and* document Y is in workspace X") is enforced at the use-case level by composing repository calls.

**Hard:**
- Four repositories is more interfaces to maintain than one Database port. The cohesion benefit outweighs the cost.
- Cross-aggregate transactions are not natively supported by the port surface. The current SQLite store can wrap multiple calls in a transaction; the adapter exposes this via a context manager (out of port scope for now) when truly needed. Most use-cases do not need cross-aggregate atomicity.

**Forecloses:**
- Use-cases reaching into SQLModel sessions directly.
- A monolithic "do anything to the database" port.

## Adapters

- **`SqliteUserRepository`, `SqliteWorkspaceRepository`, `SqliteDocumentRepository`, `SqliteAttachmentRepository`** — current. SQLModel + SQLite.
- **`Postgres*Repository`** — proposed. Same Python code (SQLModel is engine-agnostic); deployment differences.
- **`InMemory*Repository`** — test fakes. Dict-backed.

See [adapters/driven/decisions/0013-sqlite-repositories.md](../../adapters/driven/decisions/0013-sqlite-repositories.md).

## Review trigger

- A cross-aggregate transaction need that cannot be expressed by composing repository calls — at that point introduce a `UnitOfWork` port that bundles repositories in a transaction.
- The number of repositories grows past ~10 and the boundary lines start feeling arbitrary. Reconsider the aggregate decomposition.
